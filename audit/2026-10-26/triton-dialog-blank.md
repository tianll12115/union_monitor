# Triton 点击散点后详情空白：现场复现与修复

2026-10-26，用户明确空白发生在详情弹窗后，继续在其已打开的 Chrome 标签页中复现。本文补充首轮审查，不将首轮“自动化可读文本存在”的结果视为视觉正常的证明。

## 现场证据

点击 E2E 的 PR #2004 / SHA `74c6cda` 后，真实 Chrome 截图仅有顶部栏和大面积白色正文，无障碍树却存在完整 PR、7 个 workflow 和任务明细。读取实际 DOM 布局得到：

- 弹窗左/右边界为 720px / 1840px。
- `.workflow` 套用趋势列表的 `190px 746px 105px` 三列网格。
- 嵌套 `.jobs` 是第三个子元素，落入第三列，又继承 `margin-left:202px`。
- `.jobs` 的实际宽度为 **0px**，x 坐标 **1902px**，位于弹窗右边界之外。
- 正文高度 **12668.375px**，弹窗保留 `scrollTop=7790`，正文标题位于 y=-7662.15625px。

因此任务名被逐字挤成极长竖列，并横向溢出；旧滚动位置令中部只剩空白。这是可复现的真实功能缺陷，并非缺少数据，也不能以“DOM 文本不空”排除。

## 最小修复

- `#detail` 内 workflow 使用专用纵向布局，任务列表恢复完整宽度、清除趋势列表缩进；长 workflow/job 名可折行。
- 每次打开或替换 Triton 批次详情后，将弹窗的纵向和横向滚动位置归零。
- 趋势列表的网格与时间轨道布局不改。

## 门禁补强与复盘

先补充失败 UT：保留 7790px/90px 的滚动位置后打开详情，原实现没有归零。再补充浏览器用例 `[TRITON-005]`：构造 7 个 workflow、每个 3 个长 NPU 任务及失败步骤，原实现于 2560px 宽度明确违反“弹窗不得横向溢出”。

修复后同一用例在 2560、1440、390px 验证任务区域宽度 >200px、所有任务区域左右边界均在弹窗内、无横向溢出，以及滚到底关闭后打开另一个长详情时标题回到视口、scrollTop=0。

JUnit 将 TRITON-005 设为第五个必跑散点旅程；删除、跳过或失败均不得通过。保留全部既有 UT 和浏览器用例。新增滚动重置同时有 Node UT，真实 app.js VM 脚本设置源文件名以准确归属覆盖率。

首轮漏检原因：示例 job 名过短，且主要断言文本存在和弹窗可见，没有约束正文任务区域的实际宽度/边界，也没有覆盖用户已滚动的长详情。对应改进是使用生产形态的样本，验证实际几何位置与重开后的可见身份；覆盖率或测试数量不能代替这些断言。

同一 PR #2004 线上快照在本地修复代码下复验：7 个任务列表宽度均为 1080px，正文总高度 933px，弹窗 clientWidth 与 scrollWidth 均为 1120px，scrollTop=0。该结果证明真实生产形态的内容已恢复可见，而非仅验证简化 fixture。

最终在 Linux 原生独立检出中执行完整 `scripts/run_checks.py --browser`：Python 991 项（1 项既有 live-artifact 条件跳过）、Node 316 项、Chromium 55 项和 17/17 必跑旅程通过；本次修改的两行可执行 JS/Python 代码覆盖 2/2（100%），CSS 由三种视口下的实际布局断言验证。独立复核未提出阻止合入的问题。服务端 CI、部署与真实 Chrome 的刷新验证仍须分别确认。
