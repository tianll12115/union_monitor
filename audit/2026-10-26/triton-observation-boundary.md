# 发布阻断：实时采集时间边界竞争

详情弹窗修复 PR #7 合入后，部署 40265401920 与更新 main 的刷新 40266545633 均在数据质量校验中失败：workflow 的完成时间晚于采集开始时固定的 `window_end`。前一轮涉及 run 40264166009、40265676362，后一轮涉及 40266200405、40266193478。

根因是 REST 分页并非原子快照。发现列表期间 workflow 可以完成，而列表返回的是请求时的状态。旧实现却用较早的采集开始时间声称这些状态的 as-of 时间，严格质量门禁正确拒绝了矛盾数据。

修复默认实时采集的 `window_end` 为观测完成时间，`window_start` 仍保持精确 72 小时跨度。列表创建时间查询范围不扩大，单独记录 `discovery.fetch_window_end`，并在已有页面边界说明中声明：之后新创建的 run 未纳入，状态是逐页观测而非原子快照。这使发现范围与观测时间可以分别核查，不声称无法证明的完整性。

原始元数据同时保存最终统计窗口和发现边界，`--from-evidence` 重建时保留这两者。显式 `--as-of` 保持原固定截止时间语义；晚于它的完成证据继续被拒绝。未修改或放宽质量校验。

新增 UT 模拟发现开始于 12:00、返回已于 12:01 完成的 workflow、观测于 12:08 结束。原实现失败；修复后实时快照、72 小时跨度、发现截止时间、证据重建均符合预期；显式 12:00 截止和晚于 12:08 的伪未来完成时间仍被拒绝。

部署成功和真实 Chrome 验收需独立确认，不能用本地测试代替。
